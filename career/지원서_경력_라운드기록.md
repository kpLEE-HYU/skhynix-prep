### 심사관 지적
- **성과: 실과제 Lint Pilot에서 false violation 20% 감소**
  - 문제: 본문 서사는 false violation을 '해석·분류(triage)'하는 시스템인데, 성과의 첫 수치만 '발생 감소'다. 85% 자동 1차 분석과 TAT 60% 단축은 서술된 아키텍처에서 자연스럽게 유도되지만, 분류기가 어떻게 발생 자체를 20% 줄였는지는 인과가 끊겨 있다. 과대포장을 걸러내는 심사자는 정확히 이런 '서사에서 유도되지 않는 수치'에서 남의 성과 인용을 의심하며, 첫 수치가 흔들리면 뒤의 85%·60%까지 같이 의심받는다.
  - 방향: 이미 3)에 써 놓은 골든셋·지식베이스 재적립 루프와 이 수치를 한 절로 연결해 인과를 닫아라. 예: '설계자 확정 판정이 waiver·지식베이스로 재적립되며 반복성 false violation 발생 자체가 20% 감소'. 새 수치 없이 기존 서술과 기존 수치를 잇는 것만으로 이 줄이 시스템의 폐루프 증거로 바뀐다. 자수는 성과 문장의 수식어를 줄여 확보.
- **경량 LLM LoRA 파인튜닝 PoC를 사전 필터 티어로 두어 비용·지연을 관리했습니다.**
  - 문제: 문서 전체에서 유일하게 '무엇을, 무슨 기준으로'가 빠진 문장이다. 필터가 어떤 판정을 내려 무엇을 걸러 상위 티어로 보내는지, 학습 데이터가 무엇인지, PoC가 프로덕션 티어에 실제 편입됐는지가 전부 불명이고, '비용·지연 관리'는 아무 시스템에나 붙는 범용 효익 문구다. JD 주요업무 ②의 절반(도메인 특화 파인튜닝)을 이 한 문장이 담당하는데, 현업 눈에는 '파인튜닝은 단어만 아는 사람'으로 읽힐 위험이 가장 큰 지점이다.
  - 방향: 새 사실 없이 문서 내부 재료로 채워라: 필터의 판정 대상(예: 구조 분석으로 닫히는 명백 케이스를 선별하고 애매 케이스만 상위 LLM으로 escalate), 학습 원천(3)의 설계자 확정 골든셋), 티어 편입 판단 기준(같은 문단의 false negative 중심 회귀 평가 통과 여부)을 각각 한 절씩 연결하면 name-drop이 '티어링 설계 결정'으로 바뀐다. 자수는 '비용·지연을 관리했습니다'라는 범용 효익 절을 삭제해 상쇄.
- **· Agent Skill 플랫폼 운영(500명+), EDA AI Solution 평가·도입**
  - 문제: 이 JD의 우대요건 '현업 대상 AI Agent 서비스 운영 경험'에 가장 직접 대응하는 커리어 최대급 운영 신호(500명+)가 항목2 어디에도 근거 서사 없이 담당업무 꼬리 불릿으로만 등장한다. 무슨 플랫폼인지, '운영'이 무엇이었는지 한 글자도 없어서 맥락 없는 성과 인용의 전형으로 읽히고, 심사자에게 '플랫폼 설명도 못 쓰는데 500명은 어디서 왔나'라는 패딩 의심을 산다. 뒤에 붙은 'EDA AI Solution 평가·도입'은 깊이 신호가 0인 나열로 짜깁기 냄새를 더한다.
  - 방향: 운영의 실체 한 절을 붙여라 — 무슨 플랫폼이고 운영이 무엇이었는지(예: 사내 설계자 대상 Agent 스킬 배포·버전 관리·사용자 피드백의 골든셋 환류 중 사실인 것). 자수는 'EDA AI Solution 평가·도입'을 삭제해 충당하라. 맥락을 붙일 수 없다면 500명+ 자체를 빼는 편이 서류 전체 신뢰도에 이득이다. 사실이라면 이 불릿이 우대요건 정면 타격이므로 방치하지 마라.
- **Critic의 근거–결론 정합성 검증(불일치 시 재추론·반복 시 Human-in-the-loop)**
  - 문제: escalation 정책은 있는데 '정합성'을 무엇과 대조해 판정하는지가 없다. LLM-as-judge를 한 번 더 돌리는 것과, 근거 필드에 리포트 원문 라인·신호 경로 인용을 강제하고 결정적으로 대조하는 것은 신뢰성 설계상 완전히 다른 수준이며, Multi-Agent를 실운영하는 면접관이 첫 질문으로 반드시 찌르는 지점이다. 현 문장은 어느 쪽인지 판별 불가라 '검증'이라는 단어만 가져온 것으로 보일 수 있다.
  - 방향: 검증 기준 한 절만 추가하라 — 근거가 실제 리포트 라인·구조 분석 결과를 인용하는지 대조하는 citation-grounded 방식인지, 별도 judge 프롬프트 방식인지 명시. 1)에서 상대적으로 덜 벼려진 수식('대량 배치를 무인 운영했습니다' 주변)을 압축해 자수를 확보하면 구조 변경 없이 들어간다.
- **→ false violation 20%↓ (담당업무 블록1) vs 'RDC 방법론 개발 → false violation 87.7%↓' (블록2)**
  - 문제: 같은 지표명이 4줄 간격으로 20%와 87.7%로 두 번 등장한다. 20초 스캔에서 심사자는 어느 쪽이 LLM Agent의 성과인지 헷갈리거나, 최악의 경우 비LLM 방법론 성과(87.7%)를 LLM 서사에 재활용한 것으로 오독한다. 두 수치 모두 사실이라도 스캔 단계에서 의심을 사면 손해는 지원자 몫이다.
  - 방향: 블록1 화살표 줄에 항목2에 이미 있는 한정어를 재사용해 범위를 분리하라. 예: 'Lint false violation 20%↓'. 새 수치 없이 2~4자 추가로 두 지표의 스코프가 갈라지고, 오히려 'LLM 이전에도 87.7%를 만들던 사람이 LLM으로 새 영역을 열었다'는 상승 서사가 된다.

강점: 데이터 성격별 저장소 분리가 '이유'와 함께 서술됨 — 위반 리포트=파싱·정형 저장·결정적 조회, EDA 매뉴얼=rule 단위 chunking에 rule ID·툴 버전 메타필터를 건 Milvus 컬렉션, '관계가 질의 대상'인 모듈 계층·신호 의존=graph DB. 스택 이름 나열이 아니라 데이터 표현 선택의 근거가 있어, 이 항목 하나로 '진짜 만들어본 사람' 판정이 가능하다. / false negative 중심 회귀 평가 — sign-off 도메인의 비대칭 리스크(놓친 진짜 위반=실리콘 버그)를 평가 설계에 반영했고, 프롬프트·모델 변경을 회귀 트리거 이벤트로 취급한다. 이것은 데모를 만들어본 사람과 프로덕션을 운영해본 사람을 가르는 신호다. / LangGraph 어휘가 장식이 아니라 결정에 묶여 있다 — conditional edge는 deterministic/추론 분기 기준에, checkpointer는 대량 배치 중단·재개에, Critic 루프는 재추론→Human-in-the-loop escalation 정책에 각각 대응. 20초 스캔으로 시스템 구조가 머리에 그려진다. / Legacy를 MCP 서버 2종으로 표준화 + 폐쇄망 CI/CD 프로덕션 배포 — JD ③(MES/FDC/장비 인터페이스 연동)의 설계 도메인 등가물이며, 하이닉스 역시 폐쇄망 환경이라는 점에서 즉전력 신호로 읽힌다. / 정직한 라벨링 — 파인튜닝을 'PoC'로, 성과 범위를 '실과제 Lint Pilot'으로 스스로 한정했다. 과장 없는 포지셔닝이 나머지 수치(85% 자동 1차 분석→TAT 60% 단축의 인과 사슬)의 신뢰도를 끌어올린다. / 첫 문장의 문제 정의(설계 의도 해석이 필요한 false violation이 수백 종 rule 리포트에 섞여 공수 소모)가 이후 모든 아키텍처 결정 — deterministic/추론 분기, 성격별 저장소, 골든셋 재적립 — 의 이유로 일관되게 작동한다. 경험 조각의 짜깁기가 아니라 하나의 완결된 시스템 서사다.

  - 방어: LangGraph conditional edge 라우팅 함수로 rule 메타데이터 기반 분기를 재구현해 시연, 'RDC처럼 결정적으로 닫히는 영역과 해석이 남는 잔여 영역의 구분'으로 설명.
